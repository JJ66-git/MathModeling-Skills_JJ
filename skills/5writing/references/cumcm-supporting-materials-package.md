# CUMCM Supporting-Materials ZIP Workflow

Use this workflow for the National College Student Mathematical Modeling Contest (CUMCM), including the Guangdong division when its local notice applies.

## Submission contract

- Submit the contest-paper PDF as an independent, uncompressed file.
- Submit all supporting materials as one separate ZIP created with 7-Zip.
- The ZIP must be smaller than 20 MiB. This conservative gate satisfies the official "not exceeding 20 MB" limit and the requested "within 20 MB" workflow.
- Do not split the supporting materials into multiple archives.
- Put the supporting-material file list in the paper appendix.
- Also include the generated `支撑材料文件清单.md` inside the ZIP so the uploaded package remains self-describing.

## Required contents

Include every necessary item that supports the model, results, and conclusions:

- all complete and runnable source programs, including scripts and software interaction commands;
- data independently retrieved by the team, excluding original data already supplied with the problem;
- necessary large intermediate tables, results, or other evidence that does not belong in the paper body;
- `AI 工具使用详情.pdf` when the team used AI tools and the applicable rule requires it;
- minimal environment or run instructions needed to reproduce the code.

Source code has a dual-location requirement: include it in the paper appendix and in the supporting-material ZIP. If no program was used, state `本论文没有用到程序` in the appendix. If there is genuinely no supporting material, do not create an empty ZIP and state `本论文没有支撑材料` in the appendix.

## Prohibited contents and anonymity

Do not include:

- the contest commitment letter or numbering page;
- the contest-paper PDF itself;
- team member names, school names, team numbers, division/region identity, contact details, or other identifying information;
- identity-bearing folder names, file names, document properties, image metadata, comments, tracked changes, notebook outputs, or source-code headers;
- caches, virtual environments, temporary files, compiled binaries, duplicate exports, or unrelated working files.

Before packaging, inspect both visible content and metadata. Automatic filename checks are only a first gate and cannot prove anonymity.

## Canonical package layout

```text
supporting-materials/
  code/
  data/
  results/
  figures-or-tables/
  reproduction/
  AI 工具使用详情.pdf       # only when applicable
  支撑材料文件清单.md        # generated by the packaging helper
```

Omit empty folders. Use anonymous, descriptive relative paths. The archive itself may use a neutral name such as `supporting-materials.zip`; the submission system may rename it.

## Generate the manifest and ZIP

Run from Windows PowerShell:

```powershell
$skill = '<actual path to the 5writing skill>'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\package_supporting_materials.ps1" `
  -SourceDirectory ".\supporting-materials" `
  -OutputZip ".\submission\supporting-materials.zip"
```

The helper:

1. locates `7z.exe` from PATH or standard installation locations;
2. rejects an empty material directory, a non-ZIP output, output placed inside the source directory, and obvious commitment/numbering-page filenames;
3. writes `支撑材料文件清单.md` with sorted relative paths, byte sizes, and SHA-256 hashes;
4. creates a maximum-compression ZIP with 7-Zip;
5. rejects and deletes the archive when its size is greater than or equal to 20 MiB;
6. runs `7z t` and returns the archive path, exact size, SHA-256, manifest path, and material-file count.

The generated manifest deliberately does not hash itself. Do not edit it manually; rerun the helper after any material changes.

Helper success is not submission readiness. It does not prove that extracted code runs, the paper appendix matches, or all identity-bearing content and metadata are absent. Complete the independent `6verity` Step 9 checks before marking the package ready.

## Paper appendix list

Copy the manifest's relative-path list into a clearly titled appendix subsection such as `支撑材料文件列表`, then add `支撑材料文件清单.md` itself as the final appendix item. The paper appendix may omit byte counts and hashes if the contest template only needs file names. The exact relationship is: ZIP entries = manifest payload rows + the manifest file itself; paper appendix entries = the same complete ZIP entry set.

Recommended appendix form:

```text
支撑材料文件列表
1. code/main.py：模型求解主程序。
2. code/utils.py：数据处理与公共函数。
3. data/external_data.csv：自主查阅并使用的数据。
4. results/full_results.csv：正文未展开的完整计算结果。
5. AI 工具使用详情.pdf：AI 工具使用记录（适用时）。
6. 支撑材料文件清单.md：压缩包内文件校验清单。
```

Descriptions must reflect the real files. Do not list template examples that are absent from the archive.

## Size reduction when the ZIP is too large

Do not weaken the size gate and do not split the archive. Instead:

1. remove caches, environments, compiled binaries, logs unrelated to reproduction, duplicate files, and problem-supplied raw data;
2. replace duplicate raster exports with the single necessary final version;
3. reduce oversized intermediate image resolution only when readability and evidentiary value remain intact;
4. store large tabular intermediates in a compact lossless format that remains readable with supplied code;
5. rerun the packaging helper so the manifest and hashes are regenerated;
6. target below 19.5 MiB to leave operational margin even though the hard gate is below 20 MiB.

Never remove a source program, independently sourced data, or evidence required to reproduce a paper claim merely to meet the size limit. If necessary evidence cannot fit, mark packaging `BLOCKED` and resolve the artifact design before submission.

## Final verification and MD5 freeze

Before client submission:

- run `7z t supporting-materials.zip` and require exit code 0;
- confirm the exact archive size is below 20 MiB;
- extract into a temporary empty directory and compare archive paths with `支撑材料文件清单.md` and the paper appendix;
- open and validate `AI 工具使用详情.pdf` when applicable;
- verify runnable programs from the extracted copy, not only from the working directory;
- scan extracted paths, content, and metadata for identity leakage;
- keep the paper PDF and supporting ZIP as two independent files;
- close both final files before generating MD5 values in the official client;
- after MD5 generation, do not open-save, modify, recompress, or regenerate either file; if either changes, regenerate and resubmit its MD5 before the deadline.
